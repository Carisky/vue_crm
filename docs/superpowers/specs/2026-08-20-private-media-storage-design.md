# Private Task Media Storage Design

Date: 2026-08-20  
Status: Approved for implementation planning

## Purpose

Move task attachments out of `public/uploads` into a private local directory,
prevent filesystem paths and public file URLs from reaching the browser, and
support common office document formats as authenticated downloads.

The change covers task media upload, temporary uploads used while creating a
task, attachment, serialization, preview, download, deletion, video variants,
cleanup, and migration of existing files.

## Current problems

- Uploads are written below `public/uploads/tasks/media`, so knowing a URL is
  enough to bypass workspace membership checks.
- The API serializes the stored path and the frontend displays it as a link.
- Create and update requests send paths supplied by the browser back to the
  server. A client must never be trusted to select a server filesystem object.
- Deletion can accept a path supplied by the browser.
- Pending uploads are files only; they have no database owner or workspace and
  can become unmanaged orphans.
- The current upload handler buffers whole files and does not enforce a central
  format and size policy.

## Goals

- Store every new file under a private `STORAGE_ROOT` outside `public`.
- Identify files at the client boundary only by database IDs.
- Authorize every upload, read, attach, and delete operation.
- Never serialize, display, or accept a storage key or filesystem path.
- Preserve image and video preview, add inline PDF preview, and provide safe
  downloads for approved office formats.
- Support HTTP single-range requests for video playback.
- Make pending uploads attributable and automatically collectible.
- Provide a dry-run and restartable migration command for existing media.
- Keep the deployment and migration recoverable without silently losing files.

## Non-goals

- S3 or another remote object store.
- Editing office documents in the browser.
- Converting office documents with LibreOffice.
- Antivirus or content-disarm scanning. Office documents remain untrusted
  downloads and the UI must not describe them as safe.
- Public or anonymously shareable attachment links.
- Macro-enabled Office formats such as DOCM, XLSM, and PPTM.
- Multiple byte ranges in one request.

## Configuration

The server runtime configuration gains these private values:

- `STORAGE_ROOT`: absolute private storage directory. It is required in
  production. Development may default to `<project>/.data/storage`.
- `STORAGE_MAX_FILE_SIZE_MB`: maximum size per file, default `50`.
- `STORAGE_MAX_FILES_PER_UPLOAD`: maximum file count per request, default `10`.

Startup and CLI validation must reject an empty production `STORAGE_ROOT`, a
relative production path, and any root equal to or contained by the repository
`public` directory. The directory is created with restrictive permissions when
possible. Deploy documentation must require the application OS user to own or
have read/write access to it.

`STORAGE_ROOT` is never placed in public runtime config and is never returned
by an API.

## Storage abstraction

A filesystem storage module owns all disk access. Application routes and media
services work with opaque storage keys and never construct paths themselves.

The module provides operations equivalent to:

- create a random storage key;
- stream a new object to a temporary `.part` file with a byte limit;
- atomically commit a validated temporary object;
- open an object for full or ranged reading;
- inspect object size;
- remove an object idempotently;
- resolve a key only after containment validation.

Keys are generated by the server from cryptographically random UUIDs and a
fixed internal namespace. User filenames are never used in a disk path. The
resolver rejects absolute paths, traversal segments, alternate separators,
null bytes, and any resolved path outside `STORAGE_ROOT`.

Uploads use streaming multipart handling. `workspace_id` must occur before file
parts; malformed multipart ordering is rejected before file bytes are written.
The official frontend already appends `workspace_id` before `files` and keeps
that ordering as part of its request contract.

## File validation policy

The server validates the extension, normalized claimed MIME, and file content.
The browser-provided MIME alone is never authoritative.

Inline preview formats:

- JPEG, PNG, WebP, GIF;
- MP4 and WebM;
- PDF.

Download-only formats:

- SVG;
- DOC and DOCX;
- XLS and XLSX;
- PPT and PPTX;
- ODT, ODS, and ODP;
- RTF and CSV.

SVG is download-only because active SVG content is unsafe to embed without a
dedicated sanitizer. Macro-enabled Office extensions are rejected. Unknown or
mismatched formats are rejected with a generic validation response.

ZIP-based OOXML and OpenDocument files are checked for the expected internal
structure or declared package media type. Legacy DOC/XLS/PPT files must have an
OLE compound-file signature consistent with their approved extension family.
PDF, image, and video signatures are checked. RTF and CSV use bounded textual
checks because they have no dependable binary signature.

Validation happens before the object is committed and before a database row is
created. Partial files are removed on every error path.

## Database model

`TaskMedia` remains the attachment aggregate and keeps nullable `taskId` for
pending uploads. It gains:

- `storageKey String? @unique`;
- `workspaceId String` with a workspace relation and index;
- `uploadedById String?` with a user relation and index;
- `size Int`;
- `path String?` retained temporarily as a legacy migration source.

`TaskMediaVariant` gains:

- `storageKey String? @unique`;
- `size Int`;
- nullable legacy `path` during migration.

The migration backfills `workspaceId` for existing attached media through the
task relation. `uploadedById` is nullable because the historical uploader
cannot be reconstructed. New uploads always set it. New application writes
always set `storageKey` and `size`; nullable storage keys exist only to permit a
safe staged database/filesystem migration.

After the filesystem migration succeeds, migrated legacy `path` values are set
to `NULL`. Physical paths remain absent from serialized types. A later cleanup
migration may remove the legacy columns and make storage keys non-null after
production data has been audited; that cleanup is outside this change.

## Pending upload lifecycle

`POST /api/tasks/media` continues to accept multipart form data so existing
frontend progress reporting can remain. It requires an authenticated user and
workspace membership before accepting a file part.

For each valid file it:

1. streams to a temporary private object while enforcing limits;
2. validates type and content;
3. commits the object atomically;
4. creates a pending `TaskMedia` row with `taskId = NULL`, `workspaceId`, and
   `uploadedById`;
5. returns public metadata only.

The response contains:

```json
{
  "files": [
    {
      "id": "media-id",
      "name": "report.docx",
      "mime": "application/vnd.openxmlformats-officedocument.wordprocessingml.document",
      "size": 12345,
      "kind": "document"
    }
  ]
}
```

It contains no path, storage key, filesystem-derived filename, or public URL.

Create and update task payloads replace client-supplied media path objects with
`media_ids: string[]`. The attachment service accepts only pending IDs that
belong to the same workspace and were uploaded by the acting user. Attachment
is performed in a database transaction with the task mutation. IDs belonging
to another workspace, another uploader, an existing task, or a missing object
are rejected.

If task creation fails after upload, the objects remain pending and are handled
by cleanup. Pending media older than 24 hours is removed by the scheduler. The
cleanup selects eligible database rows, removes objects idempotently, and then
deletes the rows. Historical attached media with a null uploader is never
treated as pending when `taskId` is set.

## Read and download API

Authenticated content is served by:

`GET /api/tasks/media/:mediaId/content`

An optional `variant_id` query parameter selects a video variant. The server
verifies that the variant belongs to the requested media. It loads the media
row first and authorizes:

- attached media through membership in the task workspace;
- pending media only for its uploader while that uploader is still a member of
  the recorded workspace.

The endpoint derives the storage key exclusively from the authorized database
row. It sets:

- the validated `Content-Type`;
- `X-Content-Type-Options: nosniff`;
- `Content-Disposition: inline` for approved images, video, and PDF;
- `Content-Disposition: attachment` for SVG and office documents;
- an RFC 5987-compatible, CR/LF-free original filename;
- `Cache-Control: private, no-store`;
- `Accept-Ranges: bytes` for video.

Single valid ranges return `206`, `Content-Range`, and the exact content
length. Unsatisfiable or malformed ranges return `416`. Multiple ranges are
rejected. `HEAD` follows the same authorization and headers without a body.

PDF preview uses the authenticated content endpoint in the existing dialog.
No third-party viewer receives the document URL.

## Serialization and frontend

Task media serializers return:

- `id`;
- `name` from `originalName`;
- validated `mime`;
- `size`;
- derived `kind` (`image`, `video`, `pdf`, or `document`);
- variants with `id`, `mime`, resolution, and size.

They do not return `path` or `storageKey`. The frontend derives an authenticated
content endpoint from the opaque media ID only for `src`, preview, or a user
initiated download. The endpoint URL is never rendered as visible text.

The gallery displays filename, type, formatted size, and a type-specific icon.
Images and video keep their current preview behavior. PDF receives an embedded
preview. Download-only documents show a document card and a Download button.
The browser receives the final filename from `Content-Disposition`.

Upload forms use `accept` as a usability hint matching the allowlist, while the
server remains authoritative. Upload, attachment, and deletion use media IDs
only. The legacy delete body fields `path` and `workspace_id` are removed.

## Video variants

Video probing and transcoding are refactored to request private physical paths
through the storage abstraction. Generated files are first written as private
temporary objects, atomically committed, and recorded as variants with storage
keys and sizes. Variant serialization contains no paths. Playback selects a
variant by ID through the same authorized content endpoint.

Failure to generate variants does not delete a valid original upload. Partial
variant files and uncommitted rows are cleaned up, and the original remains
available.

## Deletion behavior

Deletion accepts only `media_id`. Attached media requires membership in the
task workspace. Pending media requires the original uploader and current
membership in its recorded workspace.

The service loads all object keys from the database, removes original and
variant objects idempotently, deletes the media row, and broadcasts the updated
task when attached. Missing physical files do not prevent removal of stale
database metadata. Errors exposed to clients contain no storage key or physical
path.

Deleting a task uses the same media deletion service instead of directly
resolving paths. Cleanup failures are logged with media IDs; physical paths are
not logged.

## Legacy migration command

The project adds:

```bash
npm run storage:migrate -- --dry-run
npm run storage:migrate -- --apply
```

The command uses the same validated `STORAGE_ROOT` and database configuration
as the application. The application must be stopped for `--apply` so uploads
cannot race the migration.

Dry-run:

- validates storage configuration and permissions;
- inventories legacy media and variant rows;
- resolves only paths inside `public/uploads/tasks/media`;
- reports missing, invalid, duplicate, referenced, and unreferenced files;
- estimates required space;
- performs no filesystem or database writes.

Apply mode:

1. creates a timestamped private migration source below `STORAGE_ROOT`;
2. moves the complete legacy public media directory into that private source;
   across filesystems it copies, verifies, and then removes the public source;
3. writes a manifest so interrupted execution is restartable;
4. for each referenced original and variant, copies to a `.part` object,
   verifies byte length and SHA-256, and atomically commits it;
5. updates the corresponding row with storage key, size, and derived workspace
   in a database transaction, then clears its legacy path;
6. leaves unreferenced files in the private migration source for manual audit;
7. produces a machine-readable and human-readable summary without printing
   absolute storage paths.

Rows that already have valid storage keys are skipped. A restarted command
uses the manifest and database state, making apply idempotent. If a database
update fails, the newly committed destination object for that row is removed;
the private migration source is retained. Missing source files are reported and
their rows remain unmigrated rather than being rewritten with empty metadata.

The command exits nonzero if any referenced row remains unmigrated. The server
must not be restarted on the new release until apply exits successfully.

## Deployment and rollback

Production deployment order:

1. back up the database;
2. set an absolute `STORAGE_ROOT` outside the repository public directory and
   grant it to the application OS user;
3. pull the release and run `npm ci`;
4. run `npx prisma validate`, tests, and build the release without changing the
   running database;
5. stop the application so the old release cannot write legacy rows during the
   staged schema and filesystem migration;
6. run `npx prisma migrate deploy`;
7. run storage migration dry-run and inspect its counts;
8. run storage migration apply and require a zero exit code;
9. start the application and test an image, a ranged video, a PDF, an office
   download, a forbidden cross-workspace request, and deletion;
10. retain the private migration source and database backup until acceptance.

Rollback requires stopping the application, restoring the database backup,
restoring the timestamped migration source to the legacy public location only
while the old release is active, checking out the old release, rebuilding, and
starting it. Any uploads accepted by the new release after migration must be
exported before database rollback or they will not be represented in the old
database. This is why acceptance should happen before reopening normal usage.

## Error handling and observability

Client errors distinguish unsupported type, excessive size, missing media,
forbidden access, and invalid range without returning internal details.
Filesystem failures return a generic server error.

Structured server logs include operation, media ID, workspace ID where known,
byte count, and a stable error category. They exclude storage root, storage key,
absolute path, session data, and raw multipart content. Migration summaries use
row IDs and counts rather than physical paths.

## Verification strategy

Development follows red-green TDD for storage and authorization behavior.

Unit tests cover:

- storage-root validation and containment;
- storage-key generation and traversal rejection;
- filename and `Content-Disposition` encoding;
- extension, MIME, signature, OOXML, OpenDocument, and legacy OLE checks;
- size and file-count limits;
- media authorization policy;
- single-range parsing, `206`, and `416` decisions;
- serializers containing no path or storage key;
- pending attachment ownership and workspace rules.

Integration tests use temporary directories and a test database boundary to
cover:

- streaming upload commit and partial-file cleanup;
- attach, read, range, delete, and pending cleanup flows;
- video variant storage behavior;
- dry-run producing no writes;
- apply migration, checksum verification, interruption recovery, idempotent
  rerun, missing source handling, and nonzero incomplete exit;
- absence of legacy public files after successful apply.

Final verification includes the complete test suite, Nuxt typecheck, Prisma
validation, production build, `git diff --check`, and a manual authenticated
smoke-test matrix after deployment. Code is not described as production-ready
unless these checks complete and their outputs are reviewed.
